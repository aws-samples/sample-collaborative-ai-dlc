# Bedrock credential modes

Claude Code, OpenCode and Codex reach Amazon Bedrock through a credential you configure in the
platform. There are two modes, and a scope holds one or the other:

| Mode                          | What is stored            | Lifetime                                    |
| ----------------------------- | ------------------------- | ------------------------------------------- |
| **IAM role** (preferred)      | An IAM role ARN           | Credentials minted per invocation, one hour |
| **Bearer token** (deprecated) | An Amazon Bedrock API key | Until you rotate it                         |

In role mode the platform stores no secret at all. A credential broker assumes the role you name
for each agent invocation and passes the resulting short-lived credentials to the CLI as
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN`.

One property holds in both modes and is worth understanding, because it is the reason a role is
needed at all: **the AgentCore runtime's execution role has no Bedrock model-invocation
permission**, and a test asserts it stays that way. Agents never inherit Bedrock access from the
runtime they execute in. A separate broker role performs the `AssumeRole`, so the credential
reaching an agent is always scoped and short-lived.

## Which mode is available where

| Scope                              | IAM role | Bearer token |
| ---------------------------------- | -------- | ------------ |
| **Platform** (Admin → Agents)      | Yes      | Yes          |
| **Space** (Space Settings → Agent) | Yes      | Yes          |
| **Personal** (Account Settings)    | No       | Yes          |

Personal scope is bearer-only by design: that endpoint is gated on authentication alone, so any
member could otherwise name an arbitrary role ARN for the platform to assume.

Resolution is `personal > space > platform`, independently per provider. One scope holds one
Bedrock value, so **saving a role at a scope replaces the bearer token stored there**. Both cards
warn before that happens.

## Before you start

Two values come from Terraform, in the deployment's `terraform/` directory:

```bash
# The principal your trust policy must name.
terraform -chdir=terraform output -raw credential_broker_role_arn

# The permission policy to attach to the role you create.
terraform -chdir=terraform output -raw bedrock_role_grant_policy_json
```

The broker role ARN is also shown in the Admin → Agents and space Agent cards, so you can copy it
from the UI instead.

!!! important "Terraform does not create the role"

    The role may live in an account this deployment does not manage, and its trust policy is your
    authoritative control over who may assume it. Terraform therefore **emits** the permission
    policy but creates nothing — creating the role and writing its trust policy is an operator
    step, in both the same-account and cross-account cases.

By default the broker may only assume roles whose ARN matches `arn:aws:iam::*:role/aidlc-bedrock-*`.
Either name your role to match that convention, or override
`bedrock_assumable_role_arns` in your `.tfvars`.

## Same-account setup

1. Create a role in the deployment's account, named `aidlc-bedrock-*`, with the permission policy
   from the Terraform output above.
2. Attach a trust policy naming the broker role — see the templates below. No external ID exists
   or is needed in this case.
3. Choose **IAM role** on the credential card, paste the role ARN, and save.
4. Start a stage. Within a few minutes CloudTrail shows `aidlc-<projectId>` in
   `userIdentity.arn`.

## Cross-account setup

When the role lives in another account, the platform is a third party to it and AWS's
confused-deputy protection applies, so an **external ID is required**. It is generated by the
platform, never supplied by you — a client-supplied value is rejected outright, because an
attacker who chooses the external ID defeats its purpose.

That creates a deliberate two-pass bootstrap:

1. Create the role and its trust policy naming the broker principal.
2. Save the binding. The save is **rejected**, because the trust policy cannot yet reference an
   external ID nobody has seen — and the rejection **returns the external ID** the platform
   generated for this binding.
3. Add it to the trust policy as an `sts:ExternalId` condition.
4. Save again.

The external ID is stable across those retries and is **re-readable** at any time from the card.
It is not a secret — AWS documents it as non-secret — so it is masked with an explicit reveal
rather than shown once and discarded.

## Trust policy templates

Render the document rather than retyping one, so the broker principal and the
session-name condition come from the deployment instead of from a placeholder:

```bash
terraform -chdir=terraform output -raw bedrock_role_trust_policy_json
```

**Which template you need is decided by the binding's scope, not by preference.**
A platform-scope binding is used by every space, so its trust policy has to admit
every space. A space-scope binding can be pinned to one.

### A platform-scope binding: one role, every space

What the output above renders by default.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/collaborative-ai-dlc-credential-broker-dev"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringLike": {
          "sts:RoleSessionName": "aidlc-*"
        }
      }
    }
  ]
}
```

A single-space `StringEquals` condition on a platform-scope binding denies every
space but the one named, and it is denied at credential resolution — the first
stage of a run fails, not the save. The bind-time preflight catches it, because a
platform binding has no single space to name and probes with the session name
`aidlc-preflight`, which this condition admits and a single-space one does not.

### A space-scope binding: one role, one space

`StringEquals` also accepts an array, which is preferable to a pattern when the
set of spaces is small and closed. Set `bedrock_role_trusted_space_ids` in your
`.tfvars` and the output renders this form.

```json
{
  "Condition": {
    "StringEquals": {
      "sts:RoleSessionName": "aidlc-<projectId>"
    }
  }
}
```

Substitute `<projectId>` with the space id from the space URL.

### Cross-account, with the external ID

The external ID is generated per binding when the binding is saved, so Terraform
cannot render it. Add this condition by hand, using the value the save returns.

```json
{
  "Condition": {
    "StringEquals": {
      "sts:ExternalId": "<external-id-from-the-rejected-save>",
      "sts:RoleSessionName": "aidlc-<projectId>"
    }
  }
}
```

Omitting the session-name condition lets **any** space that holds the role ARN use the role. The
platform cannot enforce that condition for you; only your trust policy can.

The `aidlc-<projectId>` format is a stability contract. Changing it would be a breaking change
requiring a migration note, precisely because trust policies depend on it.

## What happens when you save

Saving a role binding performs a real `AssumeRole` first, so a typo is caught at bind time instead
of on the first stage of a run.

The diagnosis is deliberately coarse, and that is a measured constraint rather than an omission:
STS returns a **byte-identical** `AccessDenied` for a wrong external ID, an omitted external ID, a
session-name mismatch, an untrusted principal and a role that does not exist. Only
`role-not-allowlisted` can be decided exactly, and it is decided locally without calling STS.
Everything else is reported as one `trust-policy-rejected` result that lists the candidate causes
with the exact values to check.

The preflight **fails open**: if it cannot run, the save proceeds. It is an input check, not a
security control — a trust policy can change at any time afterwards, and the broker re-checks the
role allowlist on every invocation regardless.

## Day-two behaviour

**Credentials last one hour and are not refreshed mid-stage.** A stage that runs longer than its
credential fails with the reason `credential_expired`, which is distinct from a rejected
credential: the binding is fine and a retry resolves a fresh credential through the normal path.
Note that a retry re-runs the whole stage attempt, so work done before the expiry is lost.

**Revoking a binding is not instant.** An already-minted credential can outlive the binding by up
to its remaining hour. This is an accepted risk of per-invocation minting.

**Spend is attributed per space** through `RoleSessionName=aidlc-<projectId>`, which appears in
CloudTrail in the role's account. Bedrock model-invocation logging is account-wide per Region and
captures every user's prompts and completions, so the platform does not enable it; it is an
optional operator step if you need per-request detail.

## Codex on Bedrock

Codex needs more than a credential, because it does not use the Bedrock-native API:

- It must use the **`amazon-bedrock-runtime`** provider, which requires Codex 0.149.1 or later.
  This deployment pins **0.153.4**. The older `amazon-bedrock` provider targets the legacy Mantle
  endpoint, which serves no model at all in some Regions including eu-central-1.
- The model must be a **cross-Region inference profile id** such as `global.openai.gpt-5.6-sol`. A
  bare foundation-model id is refused on this endpoint with "on-demand throughput isn't
  supported".
- The role's permission policy must allow `bedrock:InvokeModel` on
  `arn:aws:bedrock:<region>:<account>:project/default`, which the OpenAI-compatible APIs authorize
  against in addition to the model. The Terraform-emitted policy includes it.

!!! warning "Data residency"

    `global.` inference profiles route to commercial Regions worldwide, so Codex prompt content can
    leave the deployment's Region. There is no `eu.openai.*` profile, so an EU-residency-constrained
    deployment cannot use GPT-5.6 on any route today and should leave Codex unconfigured. The
    Anthropic models behind Claude Code and OpenCode are unaffected — they use `eu.anthropic.*`
    profiles and stay in-Region.

## Troubleshooting

| Symptom                                                                         | Cause                                                                                                                                      |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Save rejected, `role-not-allowlisted`                                           | The ARN does not match `bedrock_assumable_role_arns`; rename the role or override the variable                                             |
| Save rejected, `trust-policy-rejected`                                          | One of: untrusted principal, session-name mismatch, wrong or missing external ID, or the role does not exist. STS cannot distinguish these |
| Save rejected but returns an external ID                                        | Expected on the first cross-account save. Add it to the trust policy and save again                                                        |
| Stage fails `credential_expired`                                                | The stage outran its one-hour credential. Retry re-runs the attempt                                                                        |
| Stage fails `credential_resolution_failed`                                      | The broker could not mint a credential; check the binding still exists                                                                     |
| Codex fails within seconds, `cli_nonzero_exit`                                  | Usually the model id or the `project/default` grant, not the credential                                                                    |
| `401 ... not authorized to perform: bedrock:InvokeModel on ... project/default` | The role's permission policy predates the Codex OpenAI-compatible grant; re-apply the emitted policy                                       |

## Where values are stored

All in AWS Systems Manager Parameter Store:

| Value                         | Path                                                        | Type         |
| ----------------------------- | ----------------------------------------------------------- | ------------ |
| Bedrock binding (either mode) | `/<project>/<env>/…/agent-credentials/bedrock-bearer-token` | SecureString |
| External ID                   | `/<project>/<env>/…/bedrock-external-id`                    | String       |

The Bedrock parameter name is historical: it holds a bearer token in bearer mode and a JSON object
such as `{"roleArn":"arn:aws:iam::111122223333:role/aidlc-bedrock-inference"}` in role mode. The
mode is a property of the stored value, never a separate setting, which is what makes it impossible
for a mode flag and a credential to disagree. The external ID lives in its own non-secret parameter
outside `agent-credentials/`, so a rejected save cannot discard it.
